# Proposed Relational Schema Design

**Status:** Technical proposal for Workflow Step 05 only. No DBMS, persistence library, SQL dialect, schema, or migration is approved here. It does not alter requirements, domain boundaries, or decision statuses. Logical types below are portable concepts; their physical SQL types, identifier representation, timestamp precision, and decimal precision depend on the eventual technology decision (D03).

## Design rules

- `PK` means primary key; `FK` means foreign key. Identifiers are opaque keys; this proposal does not select UUID, integer, or another representation.
- Required facts use `NOT NULL`; nullable fields represent not-yet-recorded outcomes or explicitly conditional facts. A nullable column does not decide a pending workflow outcome.
- Foreign keys should normally use `RESTRICT`/`NO ACTION` for business records. Historical requests, loans, audit events, notifications, and fines should not disappear by cascading from an account or catalog record. Cascades are candidates only for pure association rows when deletion of both endpoints is explicitly allowed.
- “Candidate” or “conditional” constraints below are not approved business rules. They must not be activated until the referenced open decision is resolved.
- Do not persist a second independently writable copy-availability flag. Availability is derived from copy/catalog facts and operational records as specified by FR-006; allocation integrity is handled by the proposed current-claim relation below. Operational state vocabulary remains subject to requirements and decisions.

## Proposed tables

Types: `identifier`, `text`, `boolean`, `timestamp`, `date`, and `decimal` are logical types only. A timestamp means an unambiguous instant; whether the DBMS stores an offset, UTC-normalized value, or another representation is a later implementation choice.

### Requests, queues, reservations, and loans

| Table and purpose | Columns and constraints | Deletion behavior |
|---|---|---|
| `borrow_request` — request record (FR-007). | `request_id identifier PK NOT NULL`; `requester_account_id identifier FK NOT NULL → user_account`; `submitted_at timestamp NOT NULL`; `outcome text NULL` to record an eventual approved/rejected result (FR-009); `decision_at timestamp NULL`; `reviewer_account_id identifier FK NULL`. Target fields are intentionally not fixed: candidate `title_id FK NULL` and `copy_id FK NULL` with an XOR check only if exactly-one-target semantics are approved; alternative normalized target subtypes are possible. Candidate nullable `promotion_reservation_id identifier FK → reservation` is a request-level concurrency marker only if queue membership links this request and a marker/reset lifecycle is approved; it prevents the same request being promoted through duplicate entries. Pending-request lifecycle, reason, and resubmission remain open (D23). | Restrict deletion of requester, reviewer, target, and linked reservation while referenced. No cascade. |
| `waiting_queue` — title-associated queue concept (FR-010). | `queue_id identifier PK NOT NULL`; `title_id identifier FK NOT NULL → book_title`; no queue order or status column is prescribed. | Restrict title deletion while queue exists. Queue lifecycle is open (D11). |
| `queue_entry` — candidate queue membership row. | `entry_id identifier PK NOT NULL`; `queue_id identifier FK NOT NULL`; optional `borrow_request_id identifier FK NULL` only if the approved membership policy links requests; `entered_at timestamp NULL` only if a distinct queue-entry time is required. A candidate nullable `promotion_reservation_id identifier FK → reservation` can serve as a per-entry compare-and-set marker: only when a resolved policy permits at most one current promotion per entry, update it from NULL to the reservation ID in the promotion transaction. If multiple entries may represent one request, also use the request-level marker on `borrow_request`; guarding only the entry would not prevent a second entry for the same request from promotion. Reset/reuse rules and uniqueness/cardinality remain conditional on D11/D23. | Restrict deletion of queue and linked request/reservation while referenced. Membership, duplicates, eligibility, and removal are open. |
| `reservation` — title-associated reservation record (FR-010). | `reservation_id identifier PK NOT NULL`; `title_id identifier FK NOT NULL → book_title`; `created_at timestamp NOT NULL` as proposed record metadata. Candidate nullable `queue_entry_id identifier FK → queue_entry` records provenance only if an approved queue policy links the two; a uniqueness constraint must wait for the approved lifecycle/cardinality. Account/request linkage, status, expiry, and copy linkage are otherwise not fixed; add only after D11/D23/D39. | Restrict title deletion while reservation exists; no cascade from account/request/queue entry. |
| `loan` — active or historical borrowing record (FR-014). | `loan_id identifier PK NOT NULL`; `borrow_request_id identifier FK NULL → borrow_request` is nullable so the schema does not require every loan to originate from a request. When a loan is recorded for an approved borrow request, populate this link so FR-014 remains traceable; null must not be used to bypass that requirement. If linked, `UNIQUE(borrow_request_id)` remains conditional until request/loan cardinality is approved. `copy_id identifier FK NOT NULL → physical_copy`; `borrower_account_id identifier FK NOT NULL → user_account`; `created_at timestamp NOT NULL`; `due_date date NOT NULL`; `effective_return_at timestamp NULL` has meaning only once D25 is resolved. Add candidate `UNIQUE(loan_id, copy_id)` as the referenced key for a composite claim FK; it is logically redundant with the loan primary key but enables portable pair-reference validation. Overdue status can be derived against the approved due date; do not store an independent overdue flag. | Restrict deletion of request when linked, copy, and borrower while loan history exists. |
| `return_request` — request concerning an active loan (FR-011). | `return_request_id identifier PK NOT NULL`; `loan_id identifier FK NOT NULL → loan`; `requester_account_id identifier FK NOT NULL → user_account`; `submitted_at timestamp NOT NULL`; `outcome text NULL`; `reviewer_account_id identifier FK NULL`; `decision_at timestamp NULL`. Outcome vocabulary and review-required behavior remain open (D24); this schema does not require every return to be reviewed. | Restrict deletion of linked loan and accounts. |
| `renewal_request` — request concerning an active loan (FR-013). | `renewal_request_id identifier PK NOT NULL`; `loan_id identifier FK NOT NULL → loan`; `requester_account_id identifier FK NOT NULL → user_account`; `submitted_at timestamp NOT NULL`; `outcome text NULL`; `reviewer_account_id identifier FK NULL`; `decision_at timestamp NULL`; any resulting due-date history is conditional on D10 (D27 is merged into D10). | Restrict deletion of linked loan and accounts. |

`borrow_request` outcome storage records the decision when one is made; this does not assert one universal request lifecycle. The schema must not treat approval as a reservation or loan automatically; FR-014 establishes that an approved borrow request has a loan and due date, but timing and allocation remain unresolved.

### Copy allocation integrity proposal

| Table and purpose | Columns and constraints | Deletion behavior |
|---|---|---|
| `copy_claim` — proposed serialization point for a copy's current committed allocation. | `copy_id identifier PK NOT NULL FK → physical_copy`; `claim_kind text NOT NULL`; `reservation_id identifier NULL FK → reservation`; `loan_id identifier NULL`, participating in composite FK `(loan_id, copy_id) → loan(loan_id, copy_id)` (do not add a redundant single-column loan FK). Proposed portable `CHECK` must allow exactly two shapes: reservation kind with non-null `reservation_id` and null `loan_id`, or loan kind with non-null `loan_id` and null `reservation_id`; all other values/shapes are rejected. The composite FK ensures a loan claim cannot point to a different copy. For a reservation claim, validating that the reserved title matches the copy’s title requires comparing `reservation.title_id` with `physical_copy.title_id`; the portable design leaves this to the transaction protocol rather than duplicating title data in `copy_claim`. Candidate `UNIQUE(reservation_id)` prevents one reservation from claiming multiple copies only if that cardinality is approved. A separate `UNIQUE(loan_id)` is redundant: the loan/copy composite FK plus the claim's `copy_id` primary key already restrict a loan claim to the loan's one copy and one claim row. Exact claim eligibility and reservation-to-copy relationship remain policy-dependent. | `RESTRICT`/`NO ACTION` on all references. Claim row is released or converted in the same transaction that ends or changes the corresponding allocation; it is not historical evidence. |

The primary key on `copy_id` provides the core uniqueness guarantee: at most one claim row can commit for a copy. The shape CHECK prevents missing, double, or mismatched claim-kind/reference combinations; the composite loan FK verifies the claimed copy is the loan's copy. For reservation claims, the transaction must read and validate that the reservation title equals the physical copy's title while protecting both facts from concurrent change (for example by locking the referenced rows in the same transaction, using DBMS-specific locking syntax). A database may offer stronger cross-table/deferred constraints, but they are not assumed portable and require compatibility review after D03. The protocol must also ensure every active allocation has its required claim; the primary key alone does not guarantee that converse. A renewal request does not end an active loan allocation, so its claim remains attached to that loan and copy. Release follows only the end of the allocation under an approved policy. This remains a technical proposal, not an approved domain rule.

### Fines, notifications, audit, and proposed policy storage

| Table and purpose | Columns and constraints | Deletion behavior |
|---|---|---|
| `fine` — optional fine record (FR-015). | `fine_id identifier PK NOT NULL`; `loan_id identifier FK NULL → loan` is a conditional association only; its target, optionality, and cardinality await the domain decision on fine linkage (D09, D25; D29 merged into D09). `amount decimal NOT NULL` with physical precision/scale unresolved; `recorded_at timestamp NOT NULL`; `currency text NULL` until currency is decided. Nonnegative amount check is a candidate integrity rule only after fine semantics and rounding are approved. | If linked, restrict deletion of the loan; retain historical record. |
| `notification` — in-app notification addressed to an account (FR-017). | `notification_id identifier PK NOT NULL`; `recipient_account_id identifier FK NOT NULL → user_account`; `created_at timestamp NOT NULL`; `event_code text NOT NULL` is a proposed code whose event set is open (D33); `read_at timestamp NULL` is optional until read lifecycle is decided; message/payload representation is not specified. | Restrict account deletion while retained; retention and source linkage open. |
| `audit_event` — append-oriented significant-action record (FR-018). | `event_id identifier PK NOT NULL`; `occurred_at timestamp NOT NULL`; `actor_account_id identifier FK NULL` (“where available”); `action_code text NOT NULL`; `target_type text NULL`; `target_id identifier NULL`; additional detail only if approved. `target_type/target_id` is a portable polymorphic reference and cannot use a conventional FK; a typed association alternative would add tables and must be evaluated against D34. | No cascade; retention/deletion policy open. |
| `policy_revision` — example persistent policy representation, **proposed and unapproved**. | Candidate columns: `policy_revision_id identifier PK NOT NULL`; `policy_key text NOT NULL`; `value_kind text NOT NULL`; typed value columns such as `integer_value`, `decimal_value`, `boolean_value`, `text_value` (nullable); `effective_from timestamp NULL`; `effective_until timestamp NULL`; `revision_number identifier/integer NOT NULL`. Candidate uniqueness on `(policy_key, revision_number)` and value-shape CHECK depend on selected model. No policy keys, values, defaults, effective-date semantics, or enforcement are defined. | Restrict deletion; version retention and supersession are unresolved. Do not create until storage and policy boundaries are approved. |

The `policy_revision` row is only one candidate for the requested storage evaluation, not an approved domain entity. Its alternatives and trade-offs are in the next section. The existing domain model explicitly leaves persistent policy representation unapproved; adopting any candidate requires a decision and possibly a domain-boundary update. D03 also leaves persistence technology open.

## Configurable policy storage alternatives

No policy values or enforcement behavior are supplied here.

| Alternative | Benefits | Costs and risks | Boundary / decision dependency |
|---|---|---|---|
| Typed tables per policy family (for example, a loan-period record and a fine-rule record) | Strong relational types, ordinary constraints, simple queries and validation. | Schema changes for new policy families; effective dating/history requires explicit version tables; may overfit unsettled policy concepts. | Requires approved policy entities and fields; do not add while domain boundary is open. |
| Versioned policy records with a key, typed value columns, revision, and optional effective interval (`policy_revision` candidate above) | Preserves history and supports effective versions; typed columns can be constrained; portable relational structure. | More complex value-shape checks and application validation; cross-row non-overlapping effective periods are hard to enforce portably; generic keys still need an approved registry. | Proposed option only. Requires a decision on whether policies are persisted domain data, version semantics, and effective dates. |
| Generic key/value rows with text values | Flexible and easy to extend without new columns. | Weak type safety, fragile validation/conversion, difficult constraints and querying, errors can be deferred to runtime. | Not recommended as a default without explicit acceptance of those costs. Still requires an approved policy-key registry and ownership boundary. |
| External configuration (files/environment/deployment configuration), not relational policy rows | Keeps policy outside the database and can simplify an initial schema. | Weak audit/version history unless separately designed; updates and effective timing can diverge from transactions; secrets/config operations need separate controls. | Whether runtime library policies belong in persisted domain state or deployment configuration is not decided. Do not place secrets in the database or docs. |

**Unapproved technical recommendation:** If the approved domain later requires persistent, auditable, effective-dated policies, evaluate a versioned relational record with typed values and an explicit policy-key registry as the default candidate. It balances history and type safety better than free-form text. This does not approve a policy entity, a value, effective-date behavior, or runtime enforcement. A decision is required before adopting it; if persistence conflicts with an approved domain boundary, stop for that decision.
