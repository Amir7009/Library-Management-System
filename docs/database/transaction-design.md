# Proposed Transaction Design

**Status:** Technical design proposal for Workflow Step 05, independent of a selected DBMS. These transactions do not decide who is permitted to act, which requests are eligible, when a reservation is created, how a return is accepted, or policy values. Those remain governed by approved permissions and open decisions.

## Consistency principles

1. Treat the database transaction as the atomic boundary for one state-changing command: either all required writes commit or none do.
2. Enforce referential integrity and exclusive copy allocation in the database, not only in presentation-layer checks. The shared modular application core may request a transaction through a persistence boundary; business rules remain independent of console/API/web presentation (architecture overview and ADR-0003, still pending).
3. Any path that allocates or releases a physical copy must use the same `copy_claim` protocol. No alternate writer may create a loan/reservation allocation while bypassing it.
4. Keep request, reservation, and loan records separate. Approval is not itself a reservation; FR-014 requires a loan and due date for an approved borrow request, but timing is not defined. An unresolved policy must be evaluated before running a policy-dependent step.
5. Use referential constraints and row-level serialization/uniqueness as the final integrity guard. A preflight “is available?” read is advisory only and never sufficient to claim a copy.
6. On a deadlock or serialization failure, roll back the whole transaction and, if retryable, restart a bounded number of times with fresh reads. A `copy_claim.copy_id` uniqueness conflict is an allocation race loss: roll back dependent writes, re-read availability and eligibility, and try another candidate only if approved policy allows. Losing the queue-entry/request compare-and-set means another worker won; re-read its marker and do not blindly repeat the promotion. Do not retry validation errors, permission denials, or business rejection. After repeated contention, return a retryable conflict. A transient connection failure before commit may be retried after rollback/reconnect; if the connection is lost during commit and the outcome is unknown, do not blindly replay the command. Reconcile by a stable operation identifier/idempotency mechanism if one is approved, otherwise surface an indeterminate result for safe follow-up. Idempotency for repeated submissions remains an open design question.

## Concurrent allocation: recommended technical strategy

**Unapproved technical recommendation:** Use a `copy_claim` relation keyed by `copy_id` as the single current-claim registry. Insert the claim in the same transaction that creates the reservation allocation or loan allocation. Because `copy_id` is the primary key, the relational uniqueness constraint permits no more than one committed current claim row for a physical copy. Competing transactions can both observe a copy as apparently free, but only one can commit the insert; the other blocks or receives a unique-key conflict and must roll back and re-evaluate eligibility. This prevents two committed claims from sharing the same copy under the assumptions below.

### Correctness assumptions and limits

- All application writers, jobs, and future front ends use one shared allocation service/protocol and the same database constraints. Manual writes that bypass the protocol void the guarantee.
- A claim means one currently allocated copy. A waiting queue entry or title-level reservation without a copy allocation is not a copy claim.
- The `copy_claim.copy_id` primary key is portable relational uniqueness. FKs and a CHECK on claim shape are also standard relational concepts, although enforcement details must be verified against the selected DBMS. No vendor-specific mechanism is needed for the fundamental “at most one claim row per copy” invariant.
- The portable key constraint does not declaratively guarantee that every active loan or copy-bound reservation has exactly one claim, that a reservation title matches its claimed copy, that a claim is policy-eligible, or that a stale claim is released. The composite loan/copy FK checks loan-copy identity; reservation-title/copy equality is validated transactionally. Same-transaction write discipline and invariant checks are required. More powerful deferred/cross-table constraints, partial unique indexes, exclusion constraints, or lock syntax may be DBMS-specific alternatives; none is selected now.
- Locks can improve candidate selection and reduce conflicts but are not the correctness foundation. For a candidate copy, a transaction may lock its row if supported, then insert its claim; all paths must still honor the unique key. The exact lock syntax/isolation level is DBMS-specific and waits for D03.
- Claim release must be atomic with completion/cancellation of the allocation as permitted by approved policy. For loan return, D24/D25 determine when a copy becomes available; do not release on request submission unless that policy is approved. Reservation expiry/claim behavior depends on D11/D39.

### Allocation transaction outline

1. Begin transaction; read the candidate copy/title and relevant operational facts using a fresh snapshot. Apply only approved eligibility and permissions. If eligibility depends on an open policy, stop before claiming and surface the unresolved policy; do not substitute a recommended default.
2. Create the referenced reservation or loan row first, when one is required by the resolved workflow. Then insert the `copy_claim` row with that `copy_id` and exactly one matching reference. Immediate FKs can now validate the referenced row; no deferred-constraint behavior is assumed. For a loan, the composite FK must verify the same copy. For a reservation, validate `reservation.title_id = physical_copy.title_id` in this transaction while preventing either value from changing concurrently (using supported row locks or an equivalent DBMS-specific serialization mechanism). Do not insert a claim for a waiting queue entry alone.
3. If the claim insert succeeds, write any remaining related state, audit event, and notification only when their approved trigger applies, all in the same transaction where atomicity is required. Commit.
4. If the `copy_id` primary-key conflict occurs, roll back. Start a fresh transaction and re-read availability/eligibility. The caller may try another eligible copy or report that no eligible copy remains; whether to do so and how to order candidates is policy-dependent. Bound retries to avoid unbounded contention. Deadlock/serialization errors restart the full transaction with fresh reads; an uncertain commit result is reconciled rather than blindly replayed.
5. If the claim or any dependent write fails, roll back the claim and all newly created/changed related rows together. Never leave a committed claim without its required associated record through the normal transaction path.

This is a recommended technical serialization mechanism, not approval to allocate on borrow submission, to create reservations for every request, or to choose queue priority/tie behavior.

## Transaction workflows

### 1. Create a borrow request

**Atomic work:** verify the caller/account and authorization under the approved permissions matrix; validate the target form only after the FR-007 target semantics are resolved; insert `borrow_request` with requester and submission timestamp; insert an audit event or notification only if its approved event rule applies; commit.

No copy claim, reservation, queue entry, or loan is implied by request creation. If queue membership is required by a resolved policy, adding its entry must be part of this same transaction or have an explicitly designed outbox/recovery mechanism. On validation/permission failure, write no request. On transient database conflict, roll back and use bounded retry; protect against duplicate user resubmission only under a separately approved idempotency design.

### 2. Reserve an available copy

This workflow is conditional on an approved policy that creates a copy-bound reservation and defines eligibility/expiry (D11, D39). Read candidates from the title’s copies, using a fresh transaction view. For each candidate, insert the reservation row first, then insert its `copy_claim` row in the same transaction. Validate that the reservation title equals the candidate copy’s title. A competing claim loses on the `copy_id` primary key; roll back the reservation and all related writes, then re-read and re-evaluate using bounded retry. No candidate-order or tie-breaking rule is selected here.

If reservations are title-level and do not claim a particular copy, do not create a `copy_claim` for them. The persistent representation of a title-only reservation remains distinct from a physical-copy allocation.

### 3. Approve or reject a borrow request

Begin a transaction and re-read/lock the request as needed to avoid two conflicting decisions. Confirm the actor’s permission only when granted by approved rules; the employee review capability is described in FR-009, while broader role grants remain open. Record one outcome, decision timestamp, and reviewer. A competing decision should observe the already-recorded outcome and not overwrite it silently.

For approval, create the loan with its required due date (FR-014) when the approved workflow says the loan is recorded; do not assume every approval immediately creates the loan or reserve a copy merely because the request is approved. When recording a loan for this approved request, populate `loan.borrow_request_id` so the required request-to-loan relation is traceable; the nullable column only avoids imposing the unsupported reverse rule that every loan must have a request. If a resolved allocation workflow assigns a copy directly to the loan, insert the loan first, then insert its claim; the composite FK verifies that both identify the same copy. If an existing copy-bound reservation claim is being converted to this loan, follow the in-place conversion below. For rejection, record the rejection; do not create a loan or claim. Any notice/audit write follows the approved trigger and should be in-transaction or use a reliable post-commit delivery mechanism. If a required write fails, roll back the decision and dependent writes together.

#### Conditional reservation-to-loan claim conversion

Only if approved reservation/allocation policy binds a reservation to a copy and the approved borrow workflow converts that allocation into a loan, perform conversion in one transaction:

1. Re-read and serialize access to the existing `copy_claim` row and its reservation, queue entry/request, and target copy. Recheck eligibility and the approved conversion conditions after acquiring the guard; explicitly verify `reservation.title_id = physical_copy.title_id` before conversion, rather than relying on a prior claim-time check.
2. Insert the loan row first, including the same `copy_id`, due date, and borrow-request link when this loan fulfills an approved borrow request. Keep the optional column null only for a loan origin that is independently approved; do not infer such an origin here.
3. Update the existing claim row in place: keep `copy_id` unchanged, set `claim_kind` to `loan`, clear `reservation_id`, and set `loan_id` to the new loan. The shape CHECK and composite loan/copy FK validate the new claim. Do not insert a second row for the same copy.
4. Update reservation/request state only to the extent an approved lifecycle defines such fields and transitions. Commit all changes together. If the claim update, validation, or any dependent write fails, roll back the loan and leave the original reservation claim intact; on a concurrency conflict, start a fresh transaction and recheck the current state.

If the reservation is title-level and has no copy claim, there is no claim to convert; any later loan allocation follows the normal allocation protocol. This workflow does not decide whether reservations are copy-bound, when approvals convert them, or what queue/request states mean (D11, D23, D39).

### 4. Promote the next eligible waiting request

This workflow is conditional on D11/D23/D39/D40. Within a transaction, obtain the title queue, identify requests eligible under approved rules, and order only as approved. BR-003 requires FIFO by recorded submission time among already-eligible requests in the same applicable queue, but does not decide membership, eligibility, priority groups, timestamp ties, or handling of ineligible entries. Do not call this globally strict FIFO.

**Per-entry/request concurrency guard:** after resolving how a queue entry represents its request, serialize promotion on a stable identity before selecting a copy. Candidate schema references are `reservation.queue_entry_id`, `queue_entry.promotion_reservation_id`, and (when a request is linked) `borrow_request.promotion_reservation_id`; use them only if the approved queue model links those records. Lock the queue entry and, if present, the linked request in a consistent order, then re-read the entry, request, guard marker(s), and eligibility. Re-read the applicable queue ordering too and confirm that the selected entry is still next among eligible entries under the approved ordering. BR-003 uses recorded submission time for eligible requests in the same applicable queue; equal-time ties remain unresolved under D40. Do not skip a locked earlier eligible entry unless an approved policy permits that behavior. A conditional compare-and-set of the relevant marker(s) from NULL (or another approved prior state) is an alternative; check the affected-row count. Insert the reservation with its queue-entry provenance, claim the copy, and update the marker(s) in the same transaction. If one request can appear in multiple queue entries, serialize on and set the request-level marker as well; an entry-only guard would not prevent duplicate promotion through another entry. A competing worker must observe the marker or lose the lock/compare-and-set and must not promote the same request against another copy. The precise marker states, reset/reuse rule, and whether one or multiple promotions are permitted remain conditional on D11/D23; do not add a business status or permanent uniqueness rule before those decisions resolve. Row-level `SELECT … FOR UPDATE` (or equivalent) is DBMS-specific; conditional updates and unique constraints are portable relational candidates, but syntax and enforcement details need validation for the selected DBMS.

If the guard shows the entry/request was already promoted, do not allocate another copy for it. If a competing worker wins the guard, roll back all writes from the losing transaction and re-read the queue and marker; do not retry promotion for an entry already marked promoted. If the copy claim loses to another allocation, roll back and start a fresh transaction to re-read queue, entry, eligibility, and copy claim; a different candidate may be tried only if policy allows. Deadlock/serialization errors restart the whole transaction within a finite bound. If the chosen entry is now ineligible, how to skip, retain, or remove it is an open policy, not a schema default. No eligible result should not be converted into a decision about queue membership or reservation expiry.

### 5. Process a return or renewal

For either request, begin by loading the active loan and the submitted request. A duplicate/concurrent outcome must not overwrite an already recorded decision. The authorized actor and review path are checked against approved permission rules.

- **Return:** FR-012 allows an authorized employee to review a return request and record an outcome; it does not require every return to receive employee review. D24 remains open. Record the request and any permitted outcome atomically. Effective return date/time is unresolved under D25. Do not release the copy claim or mark the loan returned at submission or review time as a universal rule. Once policy defines the effective return event, update loan/fine-related facts and release its claim in the same transaction. Fine calculation and effective date remain open (D09, D25, D29).
- **Renewal:** Record the renewal request and, when a permitted outcome occurs, record it with the resulting due date only after the renewal rule is approved (D10, D27). Serialize concurrent changes to the loan so two outcomes cannot overwrite due-date history. Processing a renewal request does not release or replace the claim for its still-active loan; the claim remains attached to the same loan and copy until that allocation lifecycle ends under an approved policy. Renewal eligibility, authorization, outcome, due-date changes, and queue interactions remain open. Any notification/audit action is conditional on approved triggers.

On any failure after writes begin, roll back the entire state change. Retry deadlock/serialization failures only by restarting the full transaction with fresh reads and a finite limit; handle unique-claim conflicts as lost allocation races; treat a lost promotion guard as evidence to re-read rather than repeat. Do not blindly replay a command after an uncertain commit. For invalid state, denied permission, unresolved policy, or rejected outcome, return the appropriate business result without retrying as a technical conflict.

## Operational questions retained

The transaction protocol deliberately does not answer: whether staff may borrow as members (D20); queue eligibility, strict FIFO scope/ties, ineligible-entry handling, reservation creation/expiry (D11, D23, D40; D39 is merged into D11); request processing/timeout (D23); return review and effective date (D24, D25); renewal eligibility, limits, and outcome (D10; D27 is merged into D10); loan periods and due-date calculation (D13; D26 is merged into D13); fine formula (D09; D29 is merged into D09); business-hours enforcement (D18; D28 is merged into D18); permissions (D12, D30); or notification/audit triggers (D33, D34). These remain open and must be decided in their governing documentation.
