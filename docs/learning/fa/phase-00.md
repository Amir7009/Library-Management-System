# یادداشت‌های یادگیری — فاز پروژهٔ ۰۰: آماده‌سازی مخزن

> این فایل بخشی از یادداشت‌های یادگیری پروژه است که به زبان فارسی نوشته می‌شود
> (قاعدهٔ R10 در `AGENTS.md`). مستندات فنی پروژه به زبان انگلیسی و در پوشهٔ `docs/` نگهداری می‌شوند.

تاریخ: ۱۴ اکتبر ۲۰۲۶ (فاز پروژهٔ ۰۰)

## ۱) چرا یک پروژه به دستورالعمل‌های مهندسی ماندگار نیاز دارد؟

یک پروژهٔ نرم‌افزاری معمولاً طولانی‌تر از حافظهٔ هر فرد و هر جلسهٔ کاری است:

- **افراد و عامل‌ها (agents) عوض می‌شوند.** دستیارهای هوشمند هر جلسه عملاً از صفر شروع می‌کنند؛ اگر قراردادها فقط در ذهن یا در گفتگو باشند، هر بار باید همه‌چیز از نو توضیح داده شود.
- **قراردادهای شفاهی فرسوده می‌شوند.** «همیشه قبل از تغییر، وضعیت گیت را بررسی کن» تنها زمانی واقعاً اجرا می‌شود که جایی نوشته شده باشد و به آن ارجاع داده شود.
- **سند ماندگار، قرارداد است نه یادآوری.** فایلی مثل `AGENTS.md` منبع حقیقت (source of truth) برای قواعد کاری است؛ قواعد شماره‌گذاری‌شده (R01 تا R14) در بازبینی‌ها و گزارش‌ها قابل ارجاع دقیق هستند.
- **بعضی قواعد مکانیکی هم می‌شوند.** مثلاً `.gitignore` نسخهٔ اجراییِ قاعدهٔ «اطلاعات حساس و فایل‌های پشتیبان را کامیت نکن» (R07) است؛ سند می‌گوید چه چیزی نباید کامیت شود و `.gitignore` عملاً جلویش را می‌گیرد.

نکتهٔ مهم: «ماندگار» به معنای تغییرناپذیر نیست؛ به معنای «نوشته‌شده، قابل ارجاع، و صرفاً با تصمیم آگاهانه تغییرپذیر» است.

## ۲) نقش مستندسازی

مستندسازی حافظهٔ جمعی پروژه است:

- **انتقال دانش:** هر کس (یا هر عامل) که تازه به پروژه می‌رسد، بدون پرسیدن دوباره، زمینه را از `docs/` می‌فهمد.
- **ثبت تصمیم‌ها و تصمیم‌نگرفته‌ها:** فایل `open-decisions.md` نشان می‌دهد چه چیزهایی عمداً بی‌تصمیم مانده است؛ این جلوی «اختراع بی‌اجازهٔ قواعد کسب‌وکار» (R08) را می‌گیرد.
- **تعریف فرایند:** `development-workflow.md` می‌گوید هر فاز پروژه چگونه پیش می‌رود: بررسی ← برنامه ← تأیید ← اجرا ← تأییدیه ← گزارش.
- **تفکیک مخاطب:** مستندات فنی به انگلیسی (R09) برای دقت فنی، و یادداشت‌های یادگیری به فارسی (R10) برای یادگیری؛ هر کدام جای مشخص خود را دارند و با هم تناقضی ندارند.

مستند خوب مستند «زنده» است: با تغییر پروژه به‌روز می‌شود، وگرنه به بدهیِ گمراه‌کننده تبدیل می‌شود.

## ۳) تفاوت تاریخچهٔ گیت با مستندات پروژه

| | تاریخچهٔ گیت | مستندات پروژه |
|---|---|---|
| چه چیزی را ثبت می‌کند؟ | تغییراتِ کامیت‌شده و ترتیب آن‌ها | وضعیت فعلی سیستم، تصمیم‌ها و دلایل آن‌ها |
| به کدام سؤال پاسخ می‌دهد؟ | «چه چیزی، چه زمانی، با چه ترتیبی تغییر کرد؟» | «سیستم الان چگونه است و چرا این‌گونه است؟» |
| ماهیت | دنباله‌ای از وضعیت‌های ثبت‌شده (هر کامیت یک اسنپ‌شات) | سندی زنده که مدام به‌روز می‌شود |
| تغییرپذیری | **با `rebase` و `amend` قابل بازنویسی است** — «مطلقاً تغییرناپذیر» نیست، اما بازنویسی‌اش کاری آگاهانه و معمولاً پیش از اشتراک‌گذاری است | هر لحظه ویرایش و به‌روزرسانی می‌شود |

نکتهٔ آموزشی مهم: تصور رایج این است که «تاریخچهٔ گیت تغییرناپذیر است». واقعیت این است که گیت **تغییرات کامیت‌شده و ترتیب آن‌ها را ثبت می‌کند**، ولی این تاریخچه با عملیاتی مانند `git commit --amend` (اصلاح آخرین کامیت) و `git rebase` (بازنویسی دنبالهٔ کامیت‌ها) **قابل بازنویسی است**. همین ویژگی رفع اشتباه را ممکن می‌کند، و همین ویژگی باعث می‌شود مراقب باشیم تاریخچهٔ مشترک‌شده را بی‌دلیل بازنویسی نکنیم.

در مقابل، مستندات اصلاً ادعای «ضبط ترتیب رویدادها» ندارند؛ کارشان **توصیف وضعیت فعلی سیستم، تصمیم‌ها و چرایی آن‌ها**ست. اگر دنبال «چه اتفاقی افتاده» هستید سراغ `git log` بروید؛ اگر دنبال «چرا این‌طور طراحی شد» هستید سراغ `docs/`.

## ۴) چگونه تغییرات یک عامل (agent) را بازبینی کنیم؟

کار عامل‌ها نباید بدون بازبینی پذیرفته شود. گیت ابزارهای بازبینی را آماده دارد:

```bash
git status                  # چه فایل‌هایی تغییر کرده یا اضافه شده‌اند؟
git diff                    # تغییرات فایل‌های ردیابی‌شده
git diff --staged           # تغییراتی که آمادهٔ کامیت‌اند
git log --oneline -10       # کامیت‌های اخیر
git check-ignore -v مسیر    # آیا (و چرا) این فایل نادیده گرفته می‌شود؟
```

چک‌لیست بازبینی:

1. **محدوده:** آیا تغییرات در محدوده‌ای است که فاز پروژه مجاز کرده است؟ (R14)
2. **حفظ کار کاربر:** آیا فایلِ موجودِ کاربر بدون دلیل تغییر، بازنویسی یا حذف شده؟ (R03)
3. **اطلاعات حساس:** آیا رمز، توکن، کلید یا فایل پشتیبانی اضافه شده؟ (R07) — به یاد داشته باشید `.gitignore` فقط از فایل‌های «ردیابی‌نشده» محافظت می‌کند؛ رازِ قبلاً کامیت‌شده را باید حذف و کلید را عوض کرد.
4. **قواعد کسب‌وکار:** آیا جایی قاعده‌ای «از خود ساخته» شده که تصمیمش با انسان است؟ (R08)
5. **کامیت کوچک و مشخص:** هر کامیت یک تغییر منطقی، با پیام انگلیسی گویا.
6. **ادعاها را آزمایش کنید، نه اینکه باور کنید:** اگر گزارش می‌گوید «تست‌ها اجرا شد»، خروجی و مدرک بخواهید؛ اگر خروجی نبود، یعنی اجرا نشده. در این فاز پروژه هیچ تستی وجود نداشته و اجرا هم نشده است — و گزارش دقیقاً همین را می‌گوید.
